Those failures matter. They are not just cosmetic.

The six failures point to four real problem areas:

Slippage handling in compute_v5_scores() is still wrong.
Right now high slippage can increase score magnitude instead of reducing it, because slippage is subtracted directionally and then absolute value is taken afterward. In the failing test, mean score with big slippage was 0.12 versus 0.04 with no slippage. That is backwards.
Backward compatibility for symbol embedding is incomplete.
V5ForecasterConfig(n_features=...) alias exists, but the tests still expect model.model.symbol_embed.weight, while the current class exposes symbol_embedding directly and has no model wrapper.
Weekly loss cap behavior in the sweep path is not working as intended.
The tests expecting the weekly cap to reduce trades and then reset between weeks both fail because total trades come back as zero in both cases. That means the capital-protection logic is not being exercised correctly in the tested path.
One feature compatibility test still fails around regime_session_cos.
The no-timestamp fallback looks semantically right, but the test path still fails. That tells me the feature API is close, but not fully clean.

There is also one very important improvement in this zip that fixes the “good epoch logs, dead real forward month” contradiction you were seeing:

After fine-tuning, the code now does a post-training final per-symbol sweep: it reloads the chosen checkpoint, reruns validation inference, recomputes per-symbol thresholds, and writes them back into the checkpoint. That is exactly the right design and fixes the stale-threshold problem you identified earlier.
In the forward test path, there is now also an all-inf fallback: if all per-symbol thresholds are inf, it logs loudly and, when enabled, resets those bars to the effective global threshold instead of silently taking zero trades.

Those two changes are very high value.
