## What I agree with

### 1) `mu_debias` looks like the biggest signal killer

This matches everything you’ve been seeing:

* tiny score spread
* weak monotonicity
* negative `mu_r_correlation`
* thresholds collapsing into the `0.001` range

If raw `mu_R` is already weak and you subtract a slow EMA from it, you can absolutely end up with “zero plus noise.” That would make the regression head look useless even if it had a little real signal.

### 2) Action target and return target misalignment is a serious design flaw

This is a very strong point.

If:

* action label = first barrier hit
* return target = close-to-close at horizon end

then the model is being taught two different truths on the same bar. That can absolutely create:

* weak action accuracy
* unstable side confidence
* poor ranking
* one head undoing the other

I think this is a **real architecture/training issue**, not just tuning.

### 3) SIDE_BAL loss being too strong is plausible

A regime-level KL prior can help only if it lightly regularizes.
If it is too strong, it starts overriding actual bar-level labels and pushes the model toward a biased average answer.

That fits your symptom where confidence is not actually higher on winning trades.

### 4) Raw-vs-debiased gate mismatch is definitely wrong

This one is the cleanest “must-fix” item.

You cannot gate on one scale and score on another scale and expect the selected set to mean anything.

## What I would not do blindly

### I would not fully replace the quality gate with a percentile gate as the final solution yet

Task #52 has a good instinct, but there is a risk.

A percentile-based forward score gate is useful because:

* it is scale-invariant
* it avoids weird absolute-threshold mismatch
* it avoids the relax-loop mess

But it also creates a danger:

> if the score itself is bad, a percentile gate still forces you to take the “best-looking bad trades.”

So I would use Task #52 first as a **diagnostic layer**, not immediately as the permanent production gate.

## My recommended order

## Phase 1 — do Task #51 first

This is the real repair step.

Priority order inside Task #51:

1. **disable `mu_debias` by default**
2. **align `mu_R` regression target with barrier outcome when barrier_outcomes is used**
3. **reduce `SIDE_BAL_W` sharply**
4. **log per-epoch `mu_r_corr_val`, LONG/SHORT mix, and score spread**

This is the step that actually gives the model a chance to learn a coherent signal.

## Phase 2 — use Task #52 as measurement, not final doctrine

I would implement the percentile gate, but initially as:

* an audit mode
* an A/B comparison mode
* maybe an optional forward-test mode

Not as the only final production gate yet.

Because if you fix 51 and the score is still weak, percentile gating can hide the fact that the model is still mediocre.

## What I would require before calling 51 a success

After retraining with Task #51, I would demand these checks:

### Signal spread

* `score_p90 / score_p50 > 5`
* `score_p99 / score_p50 > 10`
* `mu_R_std / abs(mu_R_mean) > 2`

### Ranking quality

* score deciles should be mostly monotonic
* top decile avg R clearly above middle deciles
* `mu_r_correlation` should become positive

### Direction quality

* LONG/SHORT mix should not collapse to 95/5
* `mean_p_side_winners` should be higher than losers
* side accuracy should improve meaningfully

### Gate sanity

* quality gate should no longer need constant relax fallback
* pass rate should be stable without arbitrary rescue logic

If 51 does not materially improve those, then the issue is deeper than debias and label conflict.

## What I think is most likely to happen

My expectation:

* **disabling `mu_debias`** will immediately widen score scale
* **aligning targets** will improve action head consistency the most
* **reducing `SIDE_BAL_W`** will reduce one-sided collapse
* then the threshold system will start looking much less “crazy”

I think that is the highest-probability path.
