Here’s what I found (most important first):

1) Prediction API action mapping is wrong vs your training labels (critical)

Your training pipeline clearly uses this mapping (in data/pipeline.py):

0 = SHORT

1 = NEUTRAL

2 = LONG

But your FastAPI /predict returns actions using:

action = ["LONG", "SHORT", "HOLD"][action_idx]


and also maps probabilities like:

"LONG": probs[0], "SHORT": probs[1], "HOLD": probs[2]


That is incompatible with your trained model outputs and will flip signals.

✅ Fix needed before you trust any prediction:

Map index 0→SHORT, 1→HOLD/NEUTRAL, 2→LONG

Map probabilities accordingly

2) The server never loads your trained models (so predictions will default)

In api/server.py, ModelManager.predict() returns _default_prediction() if no models are loaded.
And there are no calls anywhere that load checkpoints at startup.

Also, /training/start is currently a stub (random metrics), not real training.

✅ Fix needed:

On server start, load the latest/best checkpoint(s) from your checkpoint directory.

Or expose an endpoint like /models/load to load a specific file.

3) Feature pipeline is not integrated into the prediction server

/predict expects you to send features already precomputed as a 2D array. The server does not:

compute indicators

scale using your fitted scalers

build sequences from candles

So if your caller sends raw candles or unscaled features, predictions will be garbage.

✅ Fix needed (choose one):

Option A (fast): ensure your client/signal-engine sends exact same scaled features used in training

Option B (best): server takes candles → runs feature engineering + scaling → builds sequence → predicts

4) The request field sequence_length isn’t used

PredictionRequest includes sequence_length, but prediction ignores it. No shape validation either.

✅ Fix needed:

validate input shape matches what the model expects (seq_len × n_features)
