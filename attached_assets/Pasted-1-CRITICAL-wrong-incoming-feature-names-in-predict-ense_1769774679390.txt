1) CRITICAL: wrong incoming_feature_names in /predict/ensemble/candles

In api/server.py inside predict_ensemble_from_candles, you build features_np using feature_cols, but then you set:

incoming_feature_names = list(feature_cols if has_full_mtf else features_df.columns)

Why this is dangerous

In the single-TF fallback, features_np = features_df[feature_cols].values, but you pass features_df.columns as names.
That can cause:

feature_names length != feature dimension → FeatureValidator returns 100×66 of fill_value (zeros)

model predicts nonsense (like ±50% bands)

✅ Fix it (must):
Always tie names to the same columns used for features_np:

incoming_feature_names = list(feature_cols)


…and also make sure feature_cols is defined consistently in both branches.

2) CRITICAL: FeatureValidator will silently zero-out the whole input if names don’t match

In training/feature_registry.py, you added a strong defensive check:

if len(feature_names) != actual_feature_dim:
    # returns full fill_value array (zeros)


That’s good for safety, but it means any tiny mismatch turns into “padded zeros” predictions.

✅ Action:

Add a hard error instead of “silent zeros” in production mode, OR

At least log a big red error and refuse prediction:

raise ValueError("feature_names length mismatch — refusing prediction")


This prevents “fake working” predictions.

3) BUG: /predict/quantile uses expected_seq but it’s NOT defined

In api/server.py inside predict_quantile(), the auto-enforcement branch uses expected_seq:

if seq_len != expected_seq:
    ...


But in this version of the file, expected_seq is never defined in that function.

✅ Fix:
Add at the top of predict_quantile() after reading features:

expected_seq = model_manager.sequence_length


Without this, your quantile endpoint can crash depending on branch execution.

4) Your /predict/quantile still allows “no feature_names” in one scenario

You improved it (good): you reject when dims don’t match.
But you still “allow” when dims match and you assume the order is correct.

That’s still a precision-killer because “dims match” does not mean “order matches”.

✅ Best fix:
Make /predict/quantile always require feature_names (no exceptions), unless you change it to be candle-based like the ensemble endpoint.

If you keep it permissive, you will get garbage quantiles randomly depending on client ordering.

5) Client is still sending the wrong shape to /predict/quantile (seq_len=1)

Your logs show:

Sequence adjusted 1 -> 100

That means the client sent only 1 timestep and you padded the rest with zeros. This will always look broken.

✅ Fix options:

Stop calling /predict/quantile from your Web-App unless you can send a full sequence.

Or send features as [100, 66] (or [1,100,66]) with correct feature_names.

Best practice: for real trading, use candle-based endpoint and let GPU server compute features.
