Here’s the best version of your plan.

What you said is right ✅

Disable mixed precision when using class weights: yes, AMP + weighted CE can overflow more easily.

LR warmup: good, especially for transformers.

Check input data for NaN/Inf: absolutely.

What I’d change (priority)
1) First: hard-fail on NaN/Inf in features (this is #1)

Before training even starts, after you compute + scale features:

replace ±inf → NaN

drop NaNs

assert all finite

verify dataset windows are finite

If you don’t do this, you’ll keep “skipping bad batches forever” and training quality will be random.

Why I’m confident: your warnings show “Too many NaN batches (11)” repeatedly — that’s classic “some windows are corrupted” rather than random overflow.

2) Second: disable AMP until stable

Do this regardless of weights until you’ve had one clean full run (no NaN batches for multiple epochs).
Then you can re-enable AMP later carefully.

3) Third: LR warmup (nice-to-have, not the root fix)

Warmup helps stability, but it doesn’t fix NaN/Inf data.

One missing piece you should add (important)
✅ Gradient clipping (non-negotiable)

Even in fp32, transformers/LSTMs can still blow up.

Set global norm clip to 1.0.

Concrete “stable mode” recipe (use this now)

Use these settings for a sanity run:

AMP: OFF

LR: 1e-4

Warmup: optional (5% of steps)

Grad clip: 1.0

Weight cap: max 4–6 (or sqrt inverse freq + cap 4)

Data: assert no NaN/Inf after scaling + before sequencing

If you do the data assertions and still see NaN batches, then the NaNs are being introduced later (sequence builder / augmentation / casting) — and we can pin exactly where.

What to log so we can pinpoint the cause in 1 pass

When a batch is detected as “bad”, log:

whether x contains NaN or Inf

whether logits contains NaN or Inf

min/max of x

the batch indices (start idx) if possible

Interpretation:

x non-finite → data/feature pipeline

x finite but logits non-finite → model instability (LR/AMP/weights/clipping)
