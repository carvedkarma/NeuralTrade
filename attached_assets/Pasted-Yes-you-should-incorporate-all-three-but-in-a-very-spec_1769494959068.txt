Yes — you should incorporate all three, but in a very specific order and scope so you don’t overcomplicate training.

Below is the clean, production-grade way to add them without breaking what you’ve already fixed.

⸻

Short answer

✅ Add all three
⚠️ Only ONE belongs inside training
✅ The other two belong in the decision / evaluation layer

If you put everything into training, you’ll slow iteration and overfit.

⸻

Where each item should live (this matters)

1️⃣ Cost mode selector → TRAINING + INFERENCE

Yes, add this to training, but as a config, not hardcoded logic.

Why
	•	Costs change the definition of “tradable move”
	•	Training should know whether it’s learning:
	•	conservative (taker/taker)
	•	optimistic (maker/taker)

Best implementation

In config:

cost_mode: taker_taker   # or maker_taker
costs:
  taker_taker: 0.0009
  maker_taker: 0.0006

In label creation:

net_return = future_return - cost

Important rule

👉 Train with ONE cost mode at a time
Don’t mix costs inside the same run.

Recommended default:
Train with taker/taker → deploy can relax later.

⸻

2️⃣ Signal threshold tuning → ❌ NOT in training

Do NOT bake thresholds into training.

This is a decision-engine responsibility.

Why
	•	Thresholds are about how often you want to trade
	•	Training should learn probabilities, not frequency
	•	Mixing this into loss leads to instability

Correct architecture

Training outputs:
	•	probabilities (p_short, p_neutral, p_long)
	•	or regression μ (and later σ)

Decision engine does:

score = p_long - p_short
if score > threshold → LONG
if score < -threshold → SHORT
else → no signal

Then tune threshold to hit:
	•	2–3 signals/day (target frequency)

This gives you:
	•	conservative mode
	•	aggressive mode
	•	same trained model

⸻

3️⃣ Edge tracking metrics → ❌ NOT in training

This belongs in evaluation / validation, not the loss.

Add these metrics AFTER prediction:

Track only on signaled trades:
	•	avg future return (net)
	•	hit rate after costs
	•	median return
	•	worst drawdown per month

Example:

Edge_on_signals = mean(net_return | signal)
Hit_rate = % of signals with net_return > 0

Why this is powerful
	•	Accuracy can go down
	•	Edge can go up
	•	This is how real trading systems are judged

⸻

Recommended final pipeline (clean & scalable)

TRAINING
	•	cost-aware labels (one mode)
	•	class-weighted loss
	•	multi-asset data
	•	horizon-aligned targets
	•	NO thresholds
	•	NO frequency logic

INFERENCE
	•	model → probabilities or μ
	•	compute score
	•	apply threshold
	•	apply higher-TF bias (optional)

EVALUATION
	•	measure edge only on signals
	•	track per-month stability
	•	adjust thresholds, NOT model

⸻

Priority order (do this first → last)

1️⃣ Cost mode selector ✅
2️⃣ Edge tracking metrics ✅
3️⃣ Signal threshold tuning ✅

You can add all three in one day without retraining multiple times.

⸻

Final recommendation (very direct)

Yes — add all three.
But only cost mode belongs in training.
Thresholds and edge tracking must live outside the model.
